# 设计评审

这个目录记的是**以真机截图为输入的设计评审**，每轮一个子目录。

为什么要落盘：截图会过时，判断会遗忘。一轮评审的价值不只在"这次改了什么"，还在于
**当时为什么这么判断**——否则下一轮会重新争论同一件事。

## 轮次

| 轮次 | 记录                                       | 输入                              | 结论                           |
| ---- | ------------------------------------------ | --------------------------------- | ------------------------------ |
| R1   | [r1/design-review.md](r1/design-review.md) | 首版四屏的真机截图（浅色 / 深色） | 材质与层级缺失；逐屏数值规格   |
| R2   | [r2/design-review.md](r2/design-review.md) | 场景台的 8 个场景 × 2 种外观      | 层级倒挂、失败没显示、气泡撞色 |

R2 的输入和前一轮不同：不再是"随便截几张屏"，而是**固定场景**
（`Debug → Scenes`，或 `pnpm verify:ui --case scenes`）。好处是评审对象可复现、
覆盖的是平时看不到的状态（审批缺选项、运行失败、断连、长会话），而且改动前后能对着
同一张图比较。

## 工作方式

评审不是"让模型说点好听的"。有效的流程是：

1. **先跑出真实截图**。用 `pnpm verify:ui --case <name>`，不是手动截屏——因为要能复现。
2. **截图交给设计评审方**（这里用 kimi k3），要求**具体到数值**：pt、颜色角色、行高。
   形容词（"更精致"）没有可执行性。
3. **对评审里的"疑似 bug"必须实测复现**再动手。R1 里那条"助手回复渲染在用户气泡
   上方"就是真的，但验证它要自己写探针（`tools/turn-probe.mjs`），不能直接照做。
4. **改完再截一轮**，放进下一个轮次。验收脚本会证明改动没有把别的弄坏。

## R1 里被实测确认的三件事

三条都是"看起来像 A、实际是 B"的类型，值得记住：

1. **消息顺序反了**（真 bug）。屏幕顺序由数组顺序决定，而本地乐观消息被 push 到
   数组末尾。用户看到的是"模型先答、用户后问"。
2. **run 期间服务端不发 `user_turns`**（协议事实）。实测 `current_run_view.user_turns`
   在 `admitting` 阶段是 `null`，权威用户轮次要等 REST 历史。原实现据此把乐观消息
   删掉，用户提问就消失了。
3. **凭据跨安装存活**（验收基建缺陷）。重装 App 不会清钥匙串，所以 `app-launch`
   期望看到登录页、实际直接进主界面。现在每个 case 开头都 `simctl keychain reset`。

## R1 里被否掉的判断

评审方提出的建议不都照做，理由要写下来：

- **给助手消息加"归属感"的气泡**——不做。Messages 里助手就是全宽文本，
  加气泡反而更不像原生。归属感靠对齐与段落排版解决。
- **首页会话行显示"消息预览"**——不做。`GET /sessions` **不返回最后一条消息**，
  伪造一个预览会让用户以为是真实内容。现在显示的是服务端确实给了的字段
  （来源通道 · 会话类型）。
