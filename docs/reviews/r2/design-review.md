# Memoh iOS 设计评审 R2

评审对象：R2 场景台的 8 个固定场景 × 2 种外观（浅色 / 深色），iPhone 模拟器。
输入命令：`pnpm verify:simulator --name scenes -- pnpm verify:ui --case scenes`。
评审方：本机视觉模型（GLM）；在此之前先用 `measure_surfaces.py` 量了一遍像素。

R1 评的是"四屏长得行不行"，R2 的重点不同：**先把所有状态变成可截图的场景**，
于是评审能覆盖审批、失败、长会话、断连这些平时看不到的界面。结论也是两类：
一类是从截图里量出来/看出来的真问题（已改），一类是评审方建议但我判断不该做的
（记在下面，免得下轮重新争论）。

---

## 1. 改了的（都有实测或上游依据）

### 1.1 用户气泡与 agent 活动卡片是同一种灰（量出来的）

`measure_surfaces.py` 在一张工具场景截图里量到：`#F0F0F4` 一种颜色占了 **49.4%**
的像素，而且同时出现在用户气泡和工具卡片的位置上。于是"我说的话"和"agent 干的
事"在屏幕上无法区分，整页是一片同色的板子。

改法：用户气泡 = `.secondarySystemBackground`（实心），agent 活动卡片 =
`.tertiarySystemBackground`（浅色下是描边容器、深色下是浮起容器）。两者必须是不同
表面，现在有断言钉住；颜色映射收敛到 `MessageBlockCell.color(for:)` 一个点上。

这条是 R1 那条"没有用到 iOS 材质系统"的具体下落。

### 1.2 工具卡片的层级是倒的（评审直接指出）

评审原话：「三张卡扫一眼，两个实心黑对勾（已完成）最抓眼，唯一在跑的 exec 卡反而
最不显眼」——权重反了，用户正等着的那个最该被看见。

原实现：`Running` 与工具名各占一行、都是 headline 字号——状态和它修饰的东西一样重。
现在：工具名是 headline（主体），状态是 `subheadline + 次要色`（修饰）且与它同一行；
执行位置从单独一行并进状态行（`Running · workspace`），不再是个悬空的词。

### 1.3 失败的构建被标成 Done，和回复自相矛盾（真 bug）

评审原话：「第三张卡写着 Done，下面的回复却说构建失败了」。

**根因不是配色，是这一行从来没渲染过**：工具卡片读 `block.error`，而协议里工具块
**没有** `error` 字段（`internal/agent/view/uimessage.go:58` 只有 `running *bool`）。
所以诊断永远是空的。现在按上游的做法从 output 内部读
（`isError` / `content[].text`，见 verified-behaviour 第 17 条）。

同时**改了场景数据**：原来那个场景结尾是一句"三个图表已重新生成；构建失败了" +
run completed，而当时还有一个工具在 running——真实 agent 循环里最终回复要等工具
结束，而且那句话声称生成了三个图表、实际只有一次写入。现在场景是一次诚实的
"进行中"切面，标题也从"失败"改成"输出里有错误"（协议层没有工具失败状态）。

### 1.4 错误正文不标红（评审指出，上游做法支持）

原来一律用次要灰，于是 `Module not found` 和普通备注没区别。上游
`tool-call-detail-generic.vue` 里 `errorText` 用 `text-destructive` 渲染、正常输出用
`text-foreground`。

两者不矛盾，是**两个不同对象**：

- **标题**保持中性 —— 不给"这一步"下失败的结论（第 15 条，上游明文规则）；
- **错误正文**照实标红 —— 它在报告 output 里确实写着的东西。

### 1.4b 完成态不贴 "Done"（两轮评审重复提出，最后发现是我多做了）

评审两次都指出"卡片写着 Done、下面一行红字说 Module not found，状态与内容打架"。

第一次我判成"评审把'这次工具调用的输出里有错误'读成了'任务失败了'"，写进了否定清单。
第二次重复出现时去查上游，发现根因：上游的 `showPendingLabel` 就等于 `title.pending`
——**它只在未完成时显示状态词**，完成之后不贴任何标签。而我给每一个完成的工具都贴了
"Done"，这才让"完成"与"输出里有错误"看起来在互相打脸。

现在只在 **running / failed** 时显示状态词。全部工具都会完成，给每一个都贴 "Done"
是一屏重复十几次的噪声；而且顺手消掉了那个矛盾：对勾表示跑完了，红字表示内容里有
错误，各说各的事实。

### 1.5 执行中要有"活的"指示（评审指出，我原来的判断是错的）

原来我给 running 用静态沙漏，理由写在注释里："不要闪烁动画，流式追加时频繁 reload
会让人分心"。

评审指出：静止的沙漏在等几秒之后会被读成**卡住了**——这正是要避免的观感。

我原来把两件事混为一谈了：**shimmer/骨架屏**（改布局、扫过一片光）确实会抖；
**UIActivityIndicatorView**（只旋转、不改布局）是 iOS 用户认得的那个"它在动"。
上游 Web 端也是给 running 加动画的（shimmer，延迟 250ms 起）。现在改用系统 spinner，
并在 `prepareForReuse` 里停掉（不可见的 spinner 还转着是白耗电）。

### 1.6 同一条命令在卡片上写两遍（量出来的）

`title` 经常就是整条命令，而 `input` 里又有 `command: 同一条命令`。实测三张卡有两张
这样。现在标题只在补充信息时显示，判定在 `MessageListMetrics.showsToolTitle`。

### 1.7 工具入参直接吐 JSON

`{"command" : "pytest -q"}` 的花括号、引号、冒号前空格全是零信息量的语法噪音。
现在扁平对象摊成 `key: value` 每行一条（与审批面板**共用同一套格式**——同一个屏幕上
两处显示同一份入参却格式不同，用户会以为是两件不同的事）；嵌套仍退回 JSON。

### 1.8 用户气泡上的 "You" 比用户自己说的话还显眼

删掉。右对齐 + 实心气泡已经说明是谁。屏幕阅读器仍会念角色（`updateAccessibility`）。

## 2. 评审提了但我没照做的

**按上下文正确、但不该在这一轮做的：**

- **"agent 回合要加分组容器/缩进轨道"** —— 方向对（现在卡片确实像独立悬浮的块）。
  但这是列表布局的结构性改动（要动 `NativeMessageList` 的分组逻辑），属于下一轮
  有充足验收信心时再做，不该塞进"修层级"这一轮。已记在这里。
- **"补输入栏和导航栏"** —— 场景页**故意**没有输入栏（真实 `ChatScreen` 有），
  它的职责只是把消息流的状态渲染出来。导航栏那部分是真的：场景页的返回链接是裸
  蓝色链接。但它是开发页面，不面向用户，优先级低。
- **"工具卡片缺耗时/时间戳/展开查看完整输出"** —— 都是真的缺口。
  `reasoning` 已经有 `duration_ms` 字段可用了；工具耗时与完整输出需要先确认服务端
  是否提供（不能伪造），留到下一轮连同 `message.output` 一起做。
- **"Running 的 workspace 不该染色"** —— 评审说得对，状态和作用域用同一个颜色会
  稀释语义。但这需要把状态行拆成两个 label，属于上面那条"工具卡片信息架构"的
  一部分，一并留到下一轮。

**我认为评审判断有误的：**

- **"失败应该把状态改成 Failed / 标红"** —— 前半对、后半错，所以这条我**部分采纳**。
  - **不该做的**：给状态**标题**染色或改成 Failed。上游 `tool-call-inline.vue:225` 明文
    写着：「非零退出码（包括 -1）或工具 isError 不等于用户任务失败……标题保持中性色，
    不附加退出码或错误染色」。工具试错是 agent 正常干活，把它染红会让正常过程看起来
    像事故、并把真正该注意的回合级错误淹掉。
  - **该做的（评审是对的）**：我原来给**完成**也贴了 "Done" 标签，于是"Done + 红字
    报错"看起来在打架。查上游发现它的 `showPendingLabel` 就等于 `title.pending`——
    **只在未完成时显示状态词**，完成之后不贴任何标签。全部工具都会完成，给每一个都
    贴一个 "Done" 是一屏重复十几次的噪声。现在只在 **running / failed** 时显示状态词。
    这样两轮评审指出的矛盾从根上消失了：对勾表示跑完了、红字表示内容里有错误，
    各说各的事实，谁也不替用户下"任务失败"的结论。
- **"只靠颜色区分状态，辅助功能不达标"** —— 前提不成立。状态**始终有文字**
  （"Running"/"Failed"），颜色只是辅助；色盲用户读文字、VoiceOver 也会念。
  现在更进一步：完成态连文字都不贴，靠图标形状（对勾 vs 转圈 vs 问号）区分，
  也不依赖颜色。

## 2b. 第四轮评审提的"给每张卡都补状态标签" —— 不做

第四轮评审（改动后）建议「给每张卡统一右上角状态标签（Running / Done / Error）」，
理由是没有标签时"成功是靠猜的"。

**不做，理由是这与已验证的上游行为冲突**，而且它和前面几轮的意见互相打架：
第一轮说"Done + 红字报错 = 矛盾"，这一轮又说要补回 Done。根因是我们在用标签
表达"结果"，而上游根本不用标签表达结果：

- `tool-call-inline.vue` 的 `showPendingLabel = title.pending` —— **只在未完成时**
  显示状态词；
- 结果好坏由**展开后的内容**表达（错误正文红色、正常输出常规色）。

我们已经按这个做了：进行中有 spinner + "Running"，失败有警告图标 + "Failed"，
输出里的错误用红字照实显示。"成功"没有标签，因为**成功是默认预期**——
它不需要被宣布，就像 iOS 的短信发送成功后不会弹一句"已送达"。

这条如果以后要推翻，需要先拿出上游之外的依据（比如真实用户测试结果），
单纯"看起来应该对称"不够。

## 3. 一条被两轮评审重复提出的意见

"Done 和红字报错矛盾" 在 R2 的两轮里都出现了，第一轮我判成"评审误解了语义"
并写进了上面的否定清单。第二轮重复出现时才去查上游的 `showPendingLabel`，
才发现**根因是我的实现多贴了一个标签**，评审看到的不适是真实的。

教训记在这里：**当同一个意见在两轮里重复出现，先假设它是对的**，去查依据——
即使第一次已经想清楚"语义上没错"。语义没错和观感别扭可以同时成立，
而这种时候通常是实现多做了什么，而不是评审不懂。

## 3. 下一轮该做的（按价值排序）

1. **工具卡片信息架构**：状态行拆成"状态 + 作用域"两个 label；补耗时；完整
   output 折叠展开（要先确认服务端给什么，不伪造）。
2. **agent 回合分组**：卡片与正文建立从属关系（缩进轨道或容器）。
3. **输入区键值分层**：上游是 `key` 用 muted、`value` 用 foreground；我们现在是
   一整串同色文字。需要把 `ToolInput` 的条目结构透出到 cell 层。
4. **iOS hosted XCTest target**：现在 UIKit 那一半断言（颜色映射、cell 复用、
   列表虚拟化、贴底）还只是源码，没接进 target。纯逻辑那 9 项已经能跑
   （`pnpm test:swift`）。
